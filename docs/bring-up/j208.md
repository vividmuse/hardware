# iPad Pro 10.5 (Cellular, J208) RAM bring-up

Facts measured by vividmuse in RAM desktop sessions on an iPad Pro 10.5
Cellular (`iPad7,4`, T8011, chip `0x8011`, board `0x06`), kernel
`7.3.0-rc1-orchard-j208` built from Hoolock `6831bc701` with the old J71b
series, firmware read from the attached iPad (iPadOS 17.7.11, 21H461).
Submitted as #42; the code from those sessions is tagged
`contrib/vividmuse-j208` and listed, with the open work, in
[`devices/j208/README.md`](../../devices/j208/README.md).

| Identity | Value |
| --- | --- |
| Product | iPad Pro 10.5 (Cellular), `iPad7,4` |
| DFU | chip `0x8011`, board `0x06` |
| Device tree | `apple,j208`; mainline `t8011-j208.dts` |
| Kernel platform | `apple-16k` |

The RAM drivers were bring-up code, so "worked" below means worked in those
sessions, not that Orchard builds it.

## Touch

The `apple_z2` variant from the sessions loaded firmware and captured valid
frames but registered no input device. The device-property order and
geometry it used are in `drivers/patches/0007` at the tag. D2400
(`apple,august-pmic`) LDO13 is enabled at `0x312` for the touch rail.

## Backlight

D2400 WLED: gate registers `0x307`–`0x309`, level at `0xb01` (high byte)
then `0xb00` (low byte), from `AppleD2400PMU` in 21H461. Brightness changed
in the sessions.

## Lightning charging

Measured in one RAM session on 2026-11-05 (same kernel), with the battery
telemetry above. The Lightning port (`/dock`, `dock,9pin`) is a Tristar
CBTL1610 plus a separate Dialog D2355 charger; Orion/Bellatrix on I2C1 belongs
to the other port (`/dock-orion`).

| Part | Fact |
| --- | --- |
| D2355 | `charger,d2355`, I2C0 `0x75`, AIC IRQ 204; 16-bit big-endian register address, 8-bit data |
| Input status | byte 6 of the 10-byte block at `0x80`: `0x00` no input, `0x42` online (D2365's encoding); seen on two boots |
| Input limit | `0x44e`, 10 mA per step (`AppleD2355Charger`, 21H461); iBoot leaves `0x08` (80 mA nominal) |
| Below-80 mA flag | `0x443` bit 2, written by the native setter before `0x44e`; clear after iBoot (`0x443` = `0x10`) |
| Tristar | `nxp,cbtl1610`-like, I2C0 `0x1a`, AIC IRQ 218; capability status `0x0c` and frame `0x20` as on J71b (CRC valid) |
| BrickID ADC | ADT `function-brick_id_voltage` on the Tristar node points at D2400 (`pmu@3c`), not the D2355 |
| Orion | `orion-ic` at I2C1 `0x13` NACKs until AOP GPIO 24 (`function-enable`) is driven; Lightning's `function-vbus_voltage` points at it, and its `function-set_charger` at the D2355 |

| Source | CBTL status | Frame | Decode |
| --- | --- | --- | --- |
| none | `0x25` | (last one latched) | status not valid |
| Mac USB-A port, USB-A cable | `0xa3` | `75 10 0c 00 00 00 00 66` | USB0 |
| USB-C charger, USB-C cable | `0xa3` | `75 10 09 08 00 00 00 a8` | USB-C |

Writes were limited to `0x44e`, each read back and restored to `0x08`.
Battery current (bq27540, pack at 95–98 %, 30–31 °C):

| `0x44e` | Source | Battery current |
| --- | --- | --- |
| `0x08` | either | −550 to −830 mA (desktop load) |
| `0x32` (500 mA) | Mac USB-A port | −251 mA (mean of 38) |
| `0x64` (1 A) | USB-C charger | +330 mA (mean of 34) |

Both changes reverted when `0x08` was restored. A RAM module that polls the
`0x80` status every 500 ms, grants 1 A to a decoded USB-C cable and 500 mA
otherwise, and floors on detach, then passed a plug cycle (USB-C, unplug, Mac
port, unplug, USB-C): +440 mA mean at 1 A, gauge status `Charging`. It reads Tristar only; Type-C CC
level, BrickID, BC1.2, PD (PortMicro CCG2 at I2C0 `0x12`) and the D2355
interrupt were not used.

Later RAM images (up to 2026-11-13) load the same module at boot. Once
the gauge reported `Full` with the cable still in, the input limit read
80 mA. The cause is not known.

## GPU (A10X)

Measured 2026-11-08 to 2026-11-13 in RAM sessions on the same kernel.
- **Kernel side:** out-of-tree modules built from this repository's T8010
  `pvr_apple` (`drivers/gpu/0001`, mailbox `soc-apple/0007`, RTKit
  `soc-apple/0013`) plus a T8011 delta. A runtime OF changeset adds the
  mailbox and GPU nodes and attaches them to `ps_gfx`.
- **Userspace:** OrchardLinux/mesa `73a49abe` with six patches.

| Fact | Value |
| --- | --- |
| Core | BVNC 13.7.12.2, `CORE_ID` `0x011b0c02`: 12 clusters (T8010: 6) |
| Firmware | AGX G9G RTBuddy payload in the 21H461 J208 kernelcache, `0x5c320` bytes. Its runtime area ends at `0x8ff04`, so the runtime window is `0x90000` (T8010 `0x8f000`). Init page, command offsets and context layouts are otherwise those of T8010's G9P |
| Registers | RGX `0x201000000`+`0x100000`, Fender `0x201d00000`+`0x5000`, IOP `0x201d20000`+`0x4000`, mailbox `0x201d24000`+`0x1000` |
| Mailbox IRQs | 185 send-empty, 186 send-not-empty, 187 recv-empty, 188 recv-not-empty (ADT `0xba 0xb9 0xbc 0xbb`, same order as T8010's `0xbe 0xbd 0xc0 0xbf`) |
| Bridges | T8011 only: `0x201f00000` and `0x201f80000`, `0x9000` each. The native PMGR after-on walk writes `+0x0 = 0xf`, `+0xc = 0xc0010005`, `+0x14 = 0xff`, `+0x18 = 0xff`, `+0x8104 = 3`, `+0x8100 = 3`, and `+0xc` reads back `0xc0010005`. The driver repeats this whenever GFX comes back on, before the mailbox starts |
| Power domains | GFX needs DWI on. When genpd powered DWI off right after GFX, the SoC hung, both at probe and after jobs; five traced runs located it. With DWI held on, power-off, resume and unload were clean. T8010 keeps DWI on through its `dwi_bl` node; the J208 tree has no consumer for `ps_dwi` |
| Performance state | No OPP table yet. State 4 was held for 10 s and is the fastest one used (T8010: 6). State 1 at 665 mV in the ADT |
| Per-cluster registers | T8011 firmware writes `0x11020`/`0x11080` (3D), `0x11030` (TA) and `0x11040` (CDM) once per cluster, and `0xfc0` once per pipe (3 pipes). The 3D register list has 42 entries (T8010: 29), TA 34 (28). With T8010's lists, the fragment job never ended |
| Scheduling token | The same rule as `drivers/gpu/0011` (entry index in bits 8–14, consecutive per channel). Found independently: two compute jobs in flight hit "Non Sequential Stamp Updates" |

Results on the device:

- **Compute.** 303 jobs, 300 of them in a burst of 27.1 ms. No faults.
- **Vulkan suite.** 38/40 cases passed: `vk-tri` 25/27 and `vk-compute-test`
  12/12. The two failures are the ones A10 also has: `TRI_LOAD=3`, and depth
  load (Mesa doesn't decode D32 load).
- **GL.** Zink GL passed 14/14 cases with the Mesa fixes below.
- **Desktop.** labwc ran its `gles2` renderer on Zink at 1668×2224 and was
  used for about 15 minutes, including Firefox, with no fault.
  - A client committing every 2 ms got 150.9 fps on GPU against 140.9 fps on
    pixman (simpledrm, no vblank).
  - The GPU runtime-suspends when idle.

Mesa changes (G9P backend):

- **A10X device info.** BVNC 13.7.12.2.
- **Vertex-shader register count.** The `VDM_STATE` vertex-shader register
  field (bits 10–15, in units of two registers) must be allocated in groups
  of four, like the kick temporaries.
  - A vertex shader with 10 registers drew nothing, both in Vulkan and
    through Zink.
  - 12, 14 and 16 registers drew.
  - Most of Zink's GL draws hit this.
- **Scanout pitch.** kmsro dumb buffers for Zink need a pitch aligned to
  64 bytes, because the PBE stride is in 64-byte units. 1668 px × 4 =
  6672 bytes was refused.
- **`vkMapMemory`.** Mapping memory that the G9P CPU copy path had already
  mapped failed with "already mapped". It now returns the existing mapping.
  Before the fix, the desktop log had 57 to 85 failures per session; after
  it, there were none in 15 minutes of use.

## Speakers

Four MAX98723 amplifiers, measured 2026-11-06 to 2026-11-13. Mapping and
playback were checked by listening.

| Fact | Value |
| --- | --- |
| Amps | I2C1 (`cn`, Lightning edge) `0x31` left, `0x32` right; I2C2 (`fh`, camera edge) `0x31` left, `0x32` right. Native index 0–3 in that order |
| Reset | AP GPIO `0x77`, shared by all four, active low; held in reset when unused. The amps answer within 10 ms of release |
| I2C1 | Disabled in the RAM DTB; enabled at runtime it bound `i2c-apple` at once. The ADT also has `orion-ic` at I2C1 `0x13` |
| Register map | MAX98927's, except that its `0x20`–`0x25` sit one higher (`0x21` PCM mode, `0x23` BSEL, `0x24`/`0x25` rate). 16-bit big-endian addresses |
| Enable order | Reset defaults have `AMP_EN = 1`, so `GLOBAL_EN` must come last: speaker gain, `AMP_EN`, `GLOBAL_EN`, one amp at a time. After each `GLOBAL_EN`, about 50 ms without I2C traffic. An access about 1 ms after it gave `i2c-apple` "Bus stuck" |
| Link | MCA2 with NCO2 at 12.288 MHz; 16 slots × 16 bit at 48 kHz (256 BCLK); AP routes `aud2`→`pin1` and `aud2`→`pin2`; SmartIO endpoint `0x2c` (TX), `0x2d` (RX) |
| Slots | TDM slot k carries amp k: portrait with the home button down, 0 home-left, 1 home-right, 2 camera-left, 3 camera-right. Stereo is L → 0 + 2, R → 1 + 3 |

- **Playback.** A RAM ALSA card (48 kHz `S16_LE`, 2 or 4 channels,
  600-frame periods) with a softvol control served Firefox through
  alsa-lib.
- **Clean runs.** A 120 s tone, 40 randomised open, close and drop cycles,
  and about 10 minutes of browser video were all clean.
- **One unexplained hang.** In an earlier session the whole iPad stopped
  during browser playback. No log was kept, and it has not happened again.

The CS42L83 codec (I2C2 `0x48`, REVID `0xb0`) is reached through MCA4:

- **Codec registers.** `MCLK_CTL` (`0x1009`) reads back 0 after a write, as
  in `cs42l83-i2c.c`'s defaults. The page register sits at `0x00`.
- **AOP switch.** The PLL locks only when the AOP I2S switch is set as well
  as the AP route:
  - AOP `pin0` (`0x210540000`) = `0x00180101`
  - AOP `mca1` (`0x21054000c`) = `0x00180818`
  - AOP `+0x3c` = `0x11`
  - output enable `0x210000600` = `0x0f`
  - AP `aud4` (`0x20a004024`) = `0x00180c18`
- **Result.** RX slot 0 then carried ADC data. No playback through the codec
  was tried.

## Bluetooth

Measured 2026-10-28, then used from the desktop in later sessions.

| Fact | Value |
| --- | --- |
| Chip | BCM4355C0 ROM: LMP subversion `0x6103`, ROM revision `0x1000`, which BlueTool maps to BCM4355C0 |
| Transport | UART3, operational rate 3,000,000 baud |
| Power | D2401 GPIO0 |
| Firmware | AngerB `MUR` HCD from 21H461 BlueTool, 93,142 bytes (459 Write_RAM records). Revision after Launch_RAM `0x1519` |
| Native init | The address from the ADT, then the 1,064-byte calibration from the ADT in five `0xfd97` packets, then a 210-byte power table through `0xfd98` (BCM4355C0 takes the unchunked path, not `0xfe0d`). Every status was 0 |
| Result | BlueZ 5.82 `hci0` powered (BR/EDR and LE), BLE scan received advertisements; Wi-Fi traffic unaffected. Pairing not tested |

This is J71t's chip (`drivers/bluetooth/0003`), so the J208 probably needs
only its compatible and node. Whether the calibration and power table are
needed under Linux is not known; the sessions always sent them.

## Internal storage (traced, not run)

From the 21H461 ADT and `AppleT8011PCIe`. Nothing below has run on the device.

| Fact | Value |
| --- | --- |
| Endpoint | `apcie/pci-bridge0/s3e`, PCI `106b:2002`, class `018002`, root port 0 (the same controller as T8010) |
| Port 0 | `0x601000000`+`0x4000`, IRQ 270; DART0 `0x601008000`+`0x4000`, IRQ 271, IOVA `0x80000000`+`0x3c000000` |
| NVMMU | `0x601004000`+`0x4000`, IRQ 272; 64 tags, 256 SGL entries |
| HMB | `0x8fe600000`, 26 MiB, IOVA `0xbc000000`; outside Linux RAM in the RAM sessions |
| GPIOs | PERST# 10, CLKREQ 13, boot-from-host 17 (native initial value low) |
| Enable order | `enableGated` calls `_enableNVMeMode` first (RC `0x14 = 1`, 100 µs, RC `0x110 = 1`), then the port hardware |
| NVMMU reset | Native writes `0x10000` to `+0x4` and polls **bit 16** until clear |
| Shared with Wi-Fi | Port 0 (storage) and port 2 (Wi-Fi) are on one root complex |

J71b trains its port 0 without the NVMMU (BL-01 to BL-03), which is why a
port-0 enumeration on the J208 is expected to work the same way.
